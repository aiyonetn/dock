# Before changing code

Read this before a change that can affect behavior, an interface/API, data flow or a symbol's name (function, class, method, variable). Not needed for changes only to docs, user-visible text/labels or comments, except the "what my request needs" check in step 1.

1. Ask yourself what my request needs that I didn't say: other screens, texts or settings that show the same thing (changing the language means menus and error messages too), an old feature this can break, how I'll open it (launcher, startup), each browser or program it must work in, Turkish letters, existing data. Do what's needed for my request to really work without asking, and tell me in one line ("Dili değiştirdim; menüler ve hata mesajları da değişti."). Something that would be a new feature, not needed for this one, you suggest in one line and park if I agree (Focus in `KURALLAR.md`); don't build it.
2. Update `HARITA.md` only when an important file or entry point is added, moved, renamed or removed, in the same commit; everyday changes don't touch it (the commit check blocks entries that no longer exist).
3. Layout: new code goes in the folder for its job (`HARITA.md`); code two parts use lives once in a shared folder, never copied. When a file takes on a second job, or the commit check says it passed ~400 lines, propose splitting it by job as its own step (an existing flat project too: propose once, don't reorganize unasked). Move code unchanged and check it still works the same; the commit check catches broken JS/HTML/CSS paths, not paths built while the program runs (search for those yourself).
4. Error handling: never swallow an error (an empty `except` / `catch`, or returning a safe-looking value that hides a failure). When something fails, show me a short plain message: what happened and what I can do ("İnternete bağlanılamadı. Bağlantını kontrol edip tekrar dene."), with no codes or blame. Write the details (time, the full error, which step) to one fixed log file kept out of git (`.gitignore`; the commit check refuses `.log` files), without passwords or keys, and name it under "Nasıl açılır" in `ILERLEME.md`.
5. A fallback (quietly doing something else when the normal way fails) is a product decision: add one only with my OK, mark it with a comment, and log every time it's used.
6. Code that reads or drives another program (a browser, another app's window or controls, a device, an outside service): before writing it, look at what that program really gives on this machine (window titles, control names, values, error pages) and write the code from that, not from what it "should" give. Copy those real values into the tests; don't invent them. Personal values (names, emails, private addresses, profile names) are replaced with fake ones of the same shape first, keeping what matters (invisible characters, Turkish letters, encoding): tests are pushed to GitHub. Real output hides things you won't guess: invisible characters, translated labels, a setting that changes behavior, another version. Looking is fine; keys or clicks follow `dogrulama.md`. If you can't look, say so before building on a guess.
7. A sub-agent saying "done" isn't enough: check its work through its tests and its diff, without redoing it unless something looks wrong.
