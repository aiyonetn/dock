# Check a change, or report a problem you found

"The tests pass" isn't "it works": tests share the assumptions the code was written with. Read this before you hand a change over (stage 4), when you review a change, and when you report a problem you found.

1. **Compare old and new when the change warrants it.** For a bug fix, a performance change or a high-risk change (`inceleme.md`), try the last working version (main or the previous commit) and the new one under the same conditions, and give both results ("önce 177–214 ms, şimdi 15–24 ms"). If the old version can't be run, say why. For an ordinary low-risk change, don't require a baseline comparison.
2. **Use it the way I will, at my pace:** start it the way I start it (something you start from your own session can stop when the session ends), leave the window open, wait a moment, type, save, check the result landed. Acting at machine speed hides timing bugs.
3. **Repeat only when it adds evidence.** The new version, when it involves saving, windows, the network or timing: 3 runs, counted ("3/3" or "2/3", not "çalıştı"); a flaky bug can pass the first try. If one run takes over 2 minutes, 2 runs are enough when both pass. The old version in a comparison: stop at its first failure, which already shows the problem; repeat (up to 3) only while it passes. Always run the project's required automated tests. Never hide a failed attempt behind a later success.
4. **Prove a cause, don't guess it:** change or remove only the suspected part and try again; if the problem goes away, that's the cause. A fix you only suggest is marked "(denemedim)".
5. **Go past the case you built for:** other inputs (`http` and `https`, empty, odd values), every app, browser or system the change claims to support. When the change works with another program, run the real path against each real one it claims (`canli-kontrol.md`). For a security check, ask "how would I get past this?": other spellings of the same value (encodings, other number forms) and other programs that read it differently.
6. **Check whether a problem is new:** if it also happens on the old version, say so ("bu değişiklikten önce de vardı").
7. **Keep successful reports short; detail failures.** On success, the short Kanıt of the closing block (`teslim.md`), tied to the task's "bitti sayılır" criteria. On a failure, report details: where you tried it (system, versions, commit), expected versus actual behavior, repeat counts where relevant, reproduction steps, what you couldn't try and why, and what you tried or suggest to fix it. Never call supported something you didn't run; a check you couldn't run for real keeps the task open (`teslim.md`). At task close, add the short result (e.g. "3/3 denendi") to that task's existing "Günlük" line in `ILERLEME.md`, not a new line; no new files for it.
8. Sending keys or clicks to my real desktop can land in whatever window is in front: ask me first, and check the target window is in front before each one.
